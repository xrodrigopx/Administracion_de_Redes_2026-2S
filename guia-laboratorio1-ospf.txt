PASO 6 - VERIFICACION DE VECINDADES Y ROUTER ID
----------------------------------------------------
Ejecutar en al menos dos routers (por ejemplo R1 y R2):
  show ip ospf neighbor

Completar la tabla con Neighbor ID, State, Dead Time, Address,
Interface para cada vecino visto.

Sobre el Router ID (RID):
Sin loopback configurada, Cisco IOS elige como RID la IP mas alta
entre TODAS las interfaces activas del router (no solo las que
corren OSPF), en el momento en que arranca el proceso OSPF.
Por eso en R1 el RID probablemente sea 192.0.2.1 (la interfaz hacia
R7), aunque esa interfaz ni siquiera participa en OSPF, porque
192.x.x.x es numericamente mayor que 172.16.x.x y 10.x.x.x.

Configurar una interfaz loopback con IP del rango 192.168.1.0/24
(ultimo octeto = numero de router) en la vecindad elegida:

  R2:
  interface loopback 0
  ip address 192.168.1.2 255.255.255.255

Reiniciar el proceso OSPF y verificar si cambia el RID:
  R2#clear ip ospf process
  Reset ALL OSPF processes? [no]: yes

Resultado esperado: el RID normalmente NO cambia con solo el clear,
porque el RID se fija al iniciar el proceso y no se recalcula solo.
Si no hay cambio, guardar la configuracion (write) y apagar/encender
el router en el simulador para forzar un reinicio completo del
proceso OSPF. Ahi si deberia cambiar, porque las interfaces loopback
tienen prioridad sobre cualquier interfaz fisica para la eleccion del
RID (sin importar el valor numerico de la IP), asi que el nuevo RID
pasa a ser 192.168.1.X.

Repetir la configuracion de loopback 0 (192.168.1.X, X = numero de
router) en el resto de los routers, guardando la configuracion en
cada uno, y reiniciar la simulacion.

PASO 8 - CONFIGURACION DEL PROTOCOLO BGP
---------------------------------------------
Objetivo: inspeccionar los LSA de tipo 5. R1 es el ASBR del AS 64496
y establece sesion BGP con R7 (AS 64497, cliente/ISP).

R1:
  conf t
  router bgp 64496
  neighbor 192.0.2.2 remote-as 64497
  neighbor 192.0.2.2 activate

R7:
  conf t
  router bgp 64497
  neighbor 192.0.2.1 remote-as 64496
  neighbor 192.0.2.1 activate

Verificar que la vecindad BGP levanta (mensaje %BGP-5-ADJCHANGE).

Configuracion completa en R1:
  conf t
  ip prefix-list PL-LAN-OUT seq 5 permit 172.16.0.0/24
  ip prefix-list PL-LAN-OUT seq 10 permit 172.17.0.0/24
  ip prefix-list PL-LAN-OUT seq 15 permit 172.18.0.0/24

  route-map RM-ISP-OUT permit 10
  match ip address prefix-list PL-LAN-OUT

  ip prefix-list PL-DEFAULT-IN seq 5 permit 0.0.0.0/0
  ip prefix-list PL-TEST-IN seq 10 permit 192.168.122.0/24

  route-map RM-ISP-IN permit 10
  match ip address prefix-list PL-DEFAULT-IN

  route-map RM-ISP-IN permit 20
  match ip address prefix-list PL-TEST-IN

  router bgp 64496
  neighbor 192.0.2.2 remote-as 64497
  address-family ipv4
  neighbor 192.0.2.2 route-map RM-ISP-IN in
  neighbor 192.0.2.2 route-map RM-ISP-OUT out
  network 172.16.0.0 mask 255.255.255.0
  network 172.17.0.0 mask 255.255.255.0
  network 172.18.0.0 mask 255.255.255.0
  exit-address-family

  router ospf 1
  default-information originate

  ip prefix-list PL-OSPF-REDIST seq 5 permit 192.168.122.0/24

  route-map RM-BGP-TO-OSPF permit 10
  match ip address prefix-list PL-OSPF-REDIST

  router ospf 1
  redistribute bgp 64496 subnets route-map RM-BGP-TO-OSPF

Configuracion completa en R7:
  conf t
  ip prefix-list PL-CLIENTE-IN seq 5 permit 172.16.0.0/24
  ip prefix-list PL-CLIENTE-IN seq 10 permit 172.17.0.0/24
  ip prefix-list PL-CLIENTE-IN seq 15 permit 172.18.0.0/24
  ip prefix-list PL-TEST-OUT seq 5 permit 192.168.122.0/24
  ip prefix-list PL-DEFAULT-OUT seq 10 permit 0.0.0.0/0

  route-map RM-CLIENTE-OUT permit 10
  match ip address prefix-list PL-TEST-OUT

  route-map RM-CLIENTE-OUT permit 20
  match ip address prefix-list PL-DEFAULT-OUT

  route-map RM-CLIENTE-IN permit 10
  match ip address prefix-list PL-CLIENTE-IN

  router bgp 64497
  neighbor 192.0.2.1 remote-as 64496
  neighbor 192.0.2.1 description PEERING_HACIA_R1_AS64496
  address-family ipv4
  neighbor 192.0.2.1 route-map RM-CLIENTE-IN in
  neighbor 192.0.2.1 route-map RM-CLIENTE-OUT out
  neighbor 192.0.2.1 default-originate
  network 192.168.122.0 mask 255.255.255.0
  exit-address-family


PASO 9 - CONFIGURACION DEL NAT
------------------------------------
Realizar un traceroute desde un PC de alguna LAN de sucursales hacia
la IP 8.8.8.8 (ANTES de configurar NAT).

Resultado esperado: NO llega a destino. El traceroute llega hasta R7
(o el primer salto detras, la puerta de enlace DHCP del nodo NAT) y
ahi se corta.
Pregunta "hasta que IP llega": la del primer salto detras de R7
(gateway DHCP del NAT).
Pregunta "que esta pasando": los paquetes salen con IP origen privada
(172.17.x.x o 172.18.x.x), que no es enrutable en Internet real, asi
que las respuestas nunca pueden volver.

Aplicar esta configuracion en R7:
  conf t
  access-list 100 permit ip any any
  ip nat inside source list 100 interface FastEthernet 0/0 overload
  interface FastEthernet 0/0
  ip nat outside
  interface FastEthernet 1/0
  ip nat inside

Volver a probar el traceroute a 8.8.8.8.
Resultado esperado: ahora SI llega a destino, porque el trafico sale
con la IP publica de R7 (NAT overload/PAT).

Conclusion a escribir: el NAT es necesario para que direcciones
privadas puedan salir a Internet, traduciendo el origen a una IP
publica.

----------------------------------------------------------------
Verificar show ip route en R1 y en R4, buscando las entradas nuevas.

Deberian aparecer:
  O*E2  -> ruta default (0.0.0.0/0) aprendida por OSPF como externa
           tipo 2 (metrica fija = 1, inyectada por
           default-information originate en R1)
  O E2  -> red 192.168.122.0/24 redistribuida desde BGP hacia OSPF

Pregunta "por que aparecen estas entradas": porque R1 es el ASBR y

PASO 11 - VERIFICACION DE LSAs
------------------------------------
Iniciar una captura de trafico entre R4 y R2, filtrando por "ospf"
en Wireshark.

En R1, reiniciar el proceso OSPF:
  R1#clear ip ospf process
  Reset ALL OSPF processes? [no]: yes

Identificar en la captura los mensajes LS de tipo 3, 4 y 5:

  Tipo 3 (Summary / Inter-Area LSA): generados por los ABR (R2, R3)
  para llevar informacion de rutas de un area a otra. Ejemplo: R2
  anuncia hacia Area 0 la red 172.17.0.0/24 de Area 1.

  Tipo 4 (ASBR Summary LSA): generado por los ABR para indicarle a
  las demas areas donde esta el ASBR (R1), ya que es el que
  redistribuye BGP hacia OSPF.

  Tipo 5 (AS External LSA): originado por R1 (ASBR) para las rutas
  externas redistribuidas (la ruta default y 192.168.122.0/24). Se
  inunda por todo el dominio OSPF (todas las areas, salvo que fueran
  stub, que no es el caso aca).

Verificar tambien con el comando:
  R2#show ip ospf database
Ahi se ven los LSA organizados por tipo, con su Link State ID y
Advertising Router.


PASO 12 - METRICAS ESTANDAR Y MODIFICACION
------------------------------------------------
Parado en R4 (o el router que corresponda), encontrar la metrica
para llegar a 172.18.0.0/24 con dos comandos:
  show ip ospf database <tipo> 172.18.0.0
  show ip route

Formula de costo OSPF por defecto en Cisco:
  costo = ancho de banda de referencia (100.000 kbps) / ancho de
          banda de la interfaz (kbps)

Con interfaces Gigabit (1.000.000 kbps): costo = 100.000/1.000.000 =
0,1, que redondea al minimo entero, 1. Por eso cada salto entre
routers con interfaces Gigabit cuesta 1 por defecto, y la metrica
total es igual a la cantidad de saltos del camino mas corto.

Modificar la metrica del enlace R2-R1 (interfaz Gigabit2/0 en R2):
  R2(config)#interface GigabitEthernet 2/0
  R2(config-if)#ip ospf cost 10

Alternativa a nivel global (ancho de banda de referencia):
  R2(config)#router ospf 1
  R2(config-router)#auto-cost reference-bandwidth 1000

Volver a analizar la metrica desde R4 hacia 172.18.0.0/24.

Justificacion esperada: al encarecer el enlace R2-R1, si existe un
camino alternativo mas barato dentro de Area 0 (por ejemplo via R5:
R2-R5-R3), OSPF va a recalcular y preferir ese camino. Importante:
si "auto-cost reference-bandwidth" se cambia solo en R2 y no en el
resto de los routers, los costos quedan inconsistentes entre
routers del mismo dominio OSPF (cada uno calcula la metrica con una
referencia distinta), lo cual en la practica real es un error comun
de configuracion que conviene mencionar en la respuesta.
